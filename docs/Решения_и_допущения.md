# Список решений и допущений

Документ фиксирует: (1) какие инженерные практики не реализованы, (2) что было решено самостоятельно там, где ТЗ не давало однозначного ответа, и (3) что осталось нереализованным. Всё перечисленное можно проверить в коде: схема БД — в [`001_init.sql`](../supabase/migrations/001_init.sql), фронтенд — в [`src/`](../src/).

## Часть 0. Нереализованные инженерные практики (tests, lint, hooks, best practices)

### Тестирование

- **Unit-тесты не написаны** — ни одного тестового фреймворка в проекте нет ([`package.json`](../package.json)). Не покрыты: утилиты и типы ([`types.ts`](../src/lib/types.ts)), логика хуков ([`AuthContext.tsx`](../src/context/AuthContext.tsx)), компоненты страниц.
- **Интеграционные тесты отсутствуют** — в первую очередь для БД: матрица переходов статусов в RPC `task_transition` и RLS-политики в [`001_init.sql`](../supabase/migrations/001_init.sql) — идеальные кандидаты на автотесты (например, через `supabase test db` / pgTAP или pg_prove). Сейчас всё проверяется только руками по инструкции в [README.md](../README.md#проверка-вручную).
- **E2E-тестов нет** (Playwright / Cypress): ключевые пользовательские сценарии — «исполнитель берёт задачу и отправляет на проверку», «постановщик возвращает задачу без комментария и получает ошибку» — не автоматизированы.
- **CI-пайплайн не настроен** — нет проверки сборки, типов и тестов при push/PR.

### Статический анализ и git-процесс

- **Linter не подключён** — нет ESLint (в т.ч. `typescript-eslint`, `eslint-plugin-react-hooks`, `eslint-plugin-react-refresh`), нет Prettier. Единообразие кода держится только на дисциплине.
- **Git-хуки при коммите не настроены** — нет `husky` + `lint-staged`, нет pre-commit (lint, type-check) и pre-push (тесты). Ошибки типов ловятся только вручную через `tsc`.
- **Нет проверки `npm audit` / Dependabot** — уязвимости зависимостей никем не отслеживаются.

### Несоблюдённые best practices React

- **Запросы к Supabase выполняются напрямую в компонентах** ([`Projects.tsx`](../src/pages/Projects.tsx), [`MyTasks.tsx`](../src/pages/MyTasks.tsx) и др.) без слоя API-функций и без кеширования через **React Query (TanStack Query)**: нет ретраев, нет инвалидации/синхронизации между вкладками, дублируется код загрузки.
- **Ошибка `error` из ответов Supabase во многих местах игнорируется или показывается минимально** — нет единого механизма обработки ошибок и отображения (toast/уведомления).
- **Состояния загрузки реализованы вручную флагами** (`useState` + `loading`), вместо декларативных статусов React Query или Suspense.
- **Нет разделения ответственности в компонентах**: страницы смешивают загрузку данных, бизнес-логику и разметку; нет кастомных хуков вида `useTasks()`, `useProject(id)`.
- **Нет мемоизации там, где она уместна** (`useMemo` для фильтрованных списков, `React.memo` для тяжёлых элементов списка) — при небольших объёмах данных некритично, но не масштабируется.
- **Ключи списков и формы не всегда семантичны**, нет валидации форм через библиотеку (react-hook-form + zod) — проверка полей делается вручную `if`.
- **Нет `ErrorBoundary`** — необработанная ошибка рендера «роняет» весь экран без дружелюбного сообщения.
- **Нет code splitting / `React.lazy`** для страниц — бандл собирается целиком (для маленького проекта некритично).

### Несоблюдённые best practices Supabase

- **Клиент создаётся без обработки `getSession`/`onAuthStateChange` гонок** — при инициализации возможен кратковременный «прыжок» UI до загрузки сессии ([`AuthContext.tsx`](../src/context/AuthContext.tsx)); официально рекомендованный паттерн (получение сессии до подписки) не применён.
- **Нет типизированного клиента**: не используется генерация типов из схемы БД (`supabase gen types typescript`) — запросы не типируются, соответствие имён колонок проверяется только в рантайме ([`supabaseClient.ts`](../src/lib/supabaseClient.ts)).
- **Обновление профиля/роли не синхронизирует `updated_at`-аудит и не логируется** — изменение роли постановщиком нигде не фиксируется (журнал ведётся только по статусам задач).
- **Единая миграция `001_init.sql` без идемпотентности** (`create` без `if not exists` / `create or replace` там, где можно) — повторный запуск части схемы упадёт с ошибкой; для продакшена лучше идемпотентные миграции.
- **Нет обработки `realtime`** — изменения задач другими пользователями не приходят на открытые экраны, данные устаревают до перезагрузки (Supabase Realtime не подключён).
- **Секреты: ключ лежит в `VITE_`-переменных** — это допустимо только потому, что используется публичный `anon`-ключ и всё закрыто RLS; при появлении привилегированных операций потребуется серверный слой (Edge Functions), которого в проекте нет.

## Часть 1. Решения и допущения

### Роли и пользователи

1. **Две роли — `manager` / `worker`.** Иерархии «директор → прораб → бригадир» и промежуточных ролей нет. ТЗ упоминало только постановщика и исполнителя — расширять не стал.
2. **Регистрация пользователей — вручную через дашборд Supabase, роль по умолчанию — исполнитель.** ТЗ сказало «самостоятельной регистрации нет», но не уточнило, _где_ тогда создавать пользователей. Принял решение: администратор создаёт аккаунты в Supabase (Authentication → Users), триггер `handle_new_user` автоматически заводит профиль с ролью `worker`, а постановщиком пользователь назначается вручную SQL-командой (см. [README.md](../README.md#2-создание-пользователей-регистрация-отключена)). Отдельного «админского интерфейса» для этого нет — см. Часть 2.
3. **Постановщиков и исполнителей может быть сколько угодно** — роли не привязаны к единственному пользователю.
4. **Все аутентифицированные пользователи видят ФИО и email коллег** (политика `profiles_select_authenticated` в [`001_init.sql`](../supabase/migrations/001_init.sql:107)). Это осознанный компромисс: без него невозможно показать в карточке задачи исполнителя и автора. ТЗ не уточняло, можно ли раскрывать список сотрудников; паролей и служебных данных в таблице профилей нет, а доступ к самим задачам закрыт отдельно.

### Жизненный цикл задачи

5. **Матрица переходов статусов зашита в базу** — единственный путь смены статуса — RPC `task_transition` ([`001_init.sql`](../supabase/migrations/001_init.sql:187)), прямые `UPDATE status` блокируются триггером `trg_block_direct_status_update`. ТЗ требовало «правильной последовательности шагов», но не указывало, _где_ её проверять — решил дублировать проверку на уровне БД, а не только UI.
6. **После возврата на доработку исполнитель продолжает работу над той же задачей** (`rework → in_progress → review`), а не получает новую. Это наиболее естественная трактовка «доработки», ТЗ явного ответа не давало.
7. **Статус «Принята» — конечный.** Обратного перехода «принята → в работу» нет: если задачу нужно переделать после приёмки, постановщик, по допущению, создаст новую задачу. ТЗ про «переоткрытие» задач не упоминало.
8. **Комментарий обязателен только при возврате на доработку.** При остальных переходах комментарий опционален (можно оставить пустым), но переданный текст всё равно попадает в историю. Уточнения из ТЗ, что писать при _приёмке_, не было.
9. **Исполнитель видит историю только своих задач; постановщик — всю** (политики `history_select_manager` / `history_select_assignee`). Кому из пользователей положено видеть журнал целиком, ТЗ не уточняло.

### Структура данных

10. **У задачи может не быть исполнителя** (`assignee_id` nullable): постановщик может завести задачу до того, как назначит человека. Случай «как статус ведёт себя у задачи без исполнителя» ТЗ не описывал — такая задача просто ждёт назначения и исполнитель её не видит.
11. **Постановщик может переназначить исполнителя** обычным редактированием задачи — отдельного статуса «передана новому исполнителю» нет.
12. **Сроков (дедлайнов), приоритетов и трудозатрат нет** — ТЗ их не требовало, и добавлять «на всякий случай» не стал, чтобы не раздувать модель. Поля легко добавить одной миграцией.
13. **Удаление объекта каскадно удаляет его задачи и историю** (`on delete cascade`). Альтернатива — запрет удаления объекта с задачами — была бы безопаснее с точки зрения сохранения истории, но ТЗ не определило поведение; выбрал простой вариант и отразил это в README как поведение, о котором стоит помнить.
14. **Объект — просто название и адрес.** Никаких статусов стройки, смет, этапов — ТЗ описывало объект только как контейнер для задач.

### Безопасность и архитектура

15. **Всё, что ТЗ требовало по безопасности, реализовано на уровне базы (RLS + триггеры + RPC), а не во фронтенде.** Интерфейс можно считать «тонким клиентом»: он лишь скрывает недоступные действия. ТЗ формулировало требования как требования к системе в целом — выбрал максимально строгий вариант.
16. **В приложении ровно одна миграция** (`001_init.sql`) вместо постепенных — схема создавалась целиком с самого начала.
17. **Стек — React + TypeScript + Vite + Supabase.** ТЗ стека могло не фиксировать: бэкенд не пишем с нуля, используем BaaS, чтобы весь акцент сделать на проверках безопасности в БД.
18. **Секреты**: в клиент попадает только публичный `anon`-ключ, `service_role` нигде не используется; `.env` в `.gitignore`. См. [`.env.example`](../.env.example).
19. **Язык интерфейса и меток статусов — русский**, названия статусов продублированы в [`types.ts`](../src/lib/types.ts:56) (`STATUS_LABELS`), чтобы БД хранила машинные значения (`new`, `review`...), а пользователь видел человеческие.

## Часть 2. Что не успели / осознанно за рамками

1. **Админский интерфейс для управления пользователями** — создание аккаунтов и назначение роли `manager` делаются через дашборд Supabase и SQL (см. README). Это самое заметное неудобство для эксплуатации.
2. **Уведомления** — нет ни email-, ни in-app-уведомлений «вас назначили исполнителем» / «задача вернулась на доработку». Исполнитель узнаёт о новых задачах только зайдя в раздел «Мои задачи».
3. **Свободные комментарии/переписка по задаче** — комментарий существует только как обязательное поле при возврате на доработку. Обсуждение задачи в нескольких репликах не поддержано.
4. **Вложения и фото** — для стройки это было бы полезно (фото выполненных работ), но в ТЗ не входило.
5. **Самостоятельный сброс/смена пароля в UI** — только штатные механизмы Supabase Auth, отдельного экрана нет.
6. **Поиск, фильтры и пагинация в списках** объектов и задач — при заметном росте объёма данных списки будут тормозить (все строки запрашиваются целиком).
7. **Автотесты и CI** — полностью описаны в [Части 0](#часть-0-нереализованные-инженерные-практики-tests-lint-hooks-best-practices): unit/интеграционные/e2e-тесты и CI не реализованы.
8. **Аудит входов в систему** — журнал ведётся только по сменам статусов задач; входы/неудачные попытки входа не логируются приложением.
9. **Мобильная адаптивность** — вёрстка проверялась на десктопе; для работы «с объекта» с телефона понадобится доработка.
10. **Down-миграции / версионирование схемы** — отката миграции нет; изменения схемы пойдут новой миграцией `002_...`.
11. **Обработка деградации сети** — ошибки Supabase в основном показываются пользователю «как есть», единого retry/offline-механизма нет.
12. **Редактирование истории** — сделано намеренно _ничего_: это не «не успел», а требование append-only, зафиксированное в Части 1 (п. 5, 15). Включено сюда для полноты картины.
