# Мини-CRM для строительной компании

Система постановки и контроля задач по объектам (стройкам).

- **Постановщик** — создаёт/редактирует/удаляет объекты и задачи, назначает исполнителей, принимает задачи или возвращает на доработку.
- **Исполнитель** — видит только свои задачи, берёт их в работу и отправляет на проверку.

Стек: **React + TypeScript + Vite** (фронтенд) и **Supabase** (PostgreSQL + Auth + RLS).

## Структура проекта

```
supabase/migrations/001_init.sql   # вся схема БД: таблицы, RLS, триггеры, RPC
src/
  lib/supabaseClient.ts            # клиент Supabase (только anon-ключ)
  lib/types.ts                     # типы и русские названия статусов
  context/AuthContext.tsx          # сессия и профиль пользователя
  pages/Login.tsx                  # вход по email и паролю
  pages/Projects.tsx               # список объектов (+ CRUD для постановщика)
  pages/ProjectDetail.tsx          # карточка объекта со списком задач
  pages/TaskDetail.tsx             # карточка задачи: действия + история
  pages/MyTasks.tsx                # «Мои задачи» исполнителя
```

## Развертывание

### 1. Проект Supabase

Создайте проект на [supabase.com](https://supabase.com), затем примените миграцию:

```bash
# вариант через Supabase CLI
supabase link --project-ref <ваш-ref>
supabase db push

# либо просто выполните содержимое supabase/migrations/001_init.sql
# в SQL Editor в дашборде Supabase
```

### 2. Создание пользователей (регистрация отключена)

Открытая регистрация не используется. Пользователи создаются вручную:

1. В дашборде Supabase: **Authentication → Users → Add user** (email + пароль, включите Auto Confirm).
2. При создании пользователя триггер `handle_new_user` автоматически создаст запись в `public.profiles` с ролью `worker` по умолчанию.
3. Назначьте роль постановщика нужным пользователям:

```sql
update public.profiles set role = 'manager' where email = 'boss@example.com';
update public.profiles set full_name = 'Иван Петров' where email = 'boss@example.com';
```

Постановщиков и исполнителей может быть сколько угодно.

### 3. Запуск фронтенда

```bash
cp .env.example .env
# заполните VITE_SUPABASE_URL и VITE_SUPABASE_ANON_KEY из
# Project Settings → API (только анонимный публичный ключ!)

npm install
npm run dev
```

## Модель данных

| Таблица               | Назначение                                                                    |
| --------------------- | ----------------------------------------------------------------------------- |
| `profiles`            | Профили пользователей: роль `manager` / `worker`                              |
| `projects`            | Объекты (стройки): название, адрес                                            |
| `tasks`               | Задачи: название, описание, объект, исполнитель, статус, автор, дата создания |
| `task_status_history` | История: кто, когда, из какого статуса в какой, комментарий                   |

### Цикл статусов задачи

```
Новая ──(исполнитель)──> В работе ──(исполнитель)──> На проверке
                              ▲                          │
                              │                          ├──(постановщик)──> Принята
        (исполнитель)         │                          │
                          На доработке <──(постановщик)──┘
                          комментарий обязателен
```

## Безопасность

Все требования выполняются **на уровне базы** — интерфейс можно обойти, безопасность сохранится:

1. **RLS включён на всех таблицах.** Исполнитель через API (в т.ч. прямым запросом к Supabase) не может прочитать чужие задачи и объекты без своих задач — политика `tasks_select_assignee` / `projects_select_worker_with_tasks` отфильтрует строки.

2. **Переходы статусов проверяются базой.** Единственный путь смены статуса — RPC `public.task_transition(task_id, to_status, comment)`:
   - матрица допустимых переходов зашита в теле функции;
   - исполнитель может менять статус только своей задачи;
   - возврат на доработку без комментария отклоняется;
   - прямые `UPDATE tasks SET status = ...` через API блокирует триггер `trg_block_direct_status_update`.

3. **Историю нельзя подделать.** У таблицы `task_status_history` нет политик INSERT/UPDATE/DELETE ни для кого; запись делает только SECURITY DEFINER-триггер при легитимной смене статуса. Все прочие права отозваны (`REVOKE ALL ... FROM anon, authenticated`). Подделать запись через API невозможно — попытка вернёт ошибку.

4. **Открытая регистрация отключена.** Фронтенд не вызывает `signUp`; пользователи создаются администратором в дашборде.

5. **Секреты.** Во фронтенд попадает только публичный `anon`-ключ (он безопасен — все права закрыты RLS). `service_role` ключ нигде не используется и не хранится: `.env` в `.gitignore`, в репозитории только `.env.example` без реальных ключей.

### Проверка вручную

Залогиньтесь исполнителем и выполните в консоли браузера:

```js
// попытка прочитать чужую задачу — вернёт пустой массив
const { data } = await supabase.from("tasks").select("*");
console.log(data); // только свои задачи

// попытка запрещённого перехода — ошибка от БД
await supabase.rpc("task_transition", {
  p_task_id: "<uuid чужой задачи>",
  p_to_status: "review",
}); // "Доступ запрещён: это не ваша задача"

// попытка подделать историю — RLS-ошибка
await supabase
  .from("task_status_history")
  .delete()
  .neq("id", "00000000-0000-0000-0000-000000000000");
```
